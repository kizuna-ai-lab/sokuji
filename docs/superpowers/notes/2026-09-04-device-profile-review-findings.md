# Device-profile design: adversarial review findings

**Date:** 2026-09-04. Two rounds of independent review that shaped `docs/superpowers/specs/2026-09-04-native-device-profile-design.md`. Round 1 reviewed the first draft (per-rung acceleration paths + a kernel micro-benchmark) against six subsystem maps; round 2 reviewed the written spec. Findings are recorded as returned, severity-sorted, so the reasons behind each design decision stay readable. ggml facts refer to v0.22.0 (commit 34dc0e5589504286cb40e13cbdae4bf2b5b4071b).


## Round 1 — first draft (2026-09-04)

Design under review: catalog rungs carry the acceleration path(s) they benefit from; native probes each path (CPU via `ggml_get_type_traits_cpu`, GPU via a timed MUL_MAT) once per device; the planner skips rungs whose path is slow or unsupported.


### Lens: probe-correctness (11)

- **[high] CPU axis is vacuous AND unreachable: vec_dot is non-NULL for every ladder type, and ggml_get_type_traits_cpu lives in the dlopen'd CPU module, not in anything libsokuji_native links** — The design answers cpu:* paths 'without timing' via ggml_get_type_traits_cpu(type)->vec_dot != NULL. In the pinned tree (ggml-src/src/ggml-cpu/ggml-cpu.c:217-408) the static type_traits_cpu table sets .vec_dot for F32, F16, BF16, Q4_K, Q5_K, Q6_K, Q8_0 and every other type the catalog ships (catalog.py:77 order_keys F16/Q8_0/Q6_K/Q5_K_M/Q4_K_M; TTS q8_0/bf16/f16 at catalog.py:1042-1143). The SIMD-vs-scalar decision is inside each vec_dot function via #ifdef, so the pointer test can never return 'no kernel' for any rung Sokuji publishes. Worse, with GGML_BACKEND_DL=ON + GGML_CPU_ALL_VARIANTS=ON (native/cmake/ggml_options.cmake:93-95) ggml-cpu is built as a MODULE (ggml-src/src/CMakeLists.txt:380-384, 486-509) — the stage dir holds libggml-cpu-armv8.*.so next to libggml-base.so — and ggml_get_type_traits_cpu (declared GGML_BACKEND_API in include/ggml-cpu.h:124, defined in ggml-cpu.c:417) is exported only from that module. It is not in the CPU registration's proc-address table either (ggml-cpu.cpp:652-683 lists set_n_threads, get_extra_bufts, get_features, set_abort_callback, numa_*, set_use_ref, threadpool_*). libsokuji_native links `ggml` and will fail to link, or resolve nothing at runtime because ggml dlopens modules RTLD_LOCAL. The repack tier (block-interleaved i8mm/AVX512 GEMM — the actual CPU speed differentiator for Q4_K/Q8_0, report §3) is gated in private traits.h and is invisible either way. Finally the planner already takes the SMALLEST quant on a CPU-only box (_tc_pick_quant docstring, planner.py:243) so no CPU answer can alter a recommendation.
  *Suggestion:* Drop cpu:* from the vocabulary and from sk_probe_accel. If a machine-level CPU fact is ever wanted, read it once from ggml_backend_reg_get_proc_address(cpu_reg, "ggml_backend_get_features") (this one IS in the proc table) and store it on Machine, not per rung. Do not attempt to call ggml_get_type_traits_cpu from the host library.

- **[high] 'vulkan:kquant_mmv' is a build-time constant with no reference path to compare against; the report's q6_k claim is wrong for the pinned tree** — The dedicated mul_mat_vec_<type>.comp shaders are a property of the wheel, not the device: mul_mat_vec_q2_k..q6_k.comp are all present in ggml-src/src/ggml-vulkan/vulkan-shaders/ (mul_mat_vec_q6_k.comp exists — the capability report §3 says q6_k is generic; it is not in v0.22.0). Every Vulkan device that runs this wheel gets the same shader, so a per-device probe of this path id can only ever report the same thing and there is no toggle to produce the 'generic reference' the design divides by — GGML_VK_DISABLE_* env vars exist for COOPMAT, COOPMAT2, INTEGER_DOT_PRODUCT, BFLOAT16, F16, MMVQ (ggml-vulkan.cpp:6232-6265, 6441, 7084-7087) but none for the dedicated K-quant mmv shader. The device-dependent Vulkan facts are only: integer_dot_product (→ mmvq/mmq), coopmat/coopmat2 (→ mul_mm_cm2), fp16, bf16 — and each is read once at instance/device init from the env, so a 'reference' timing needs a SEPARATE subprocess with the env var set, doubling the probe matrix.
  *Suggestion:* Delete kquant_mmv from the vocabulary. For the four real Vulkan variables either (a) parse the private booleans from the device-init log line 'ggml_vulkan: %zu = %s (%s) | uma | fp16 | bf16 | fp4 | warp size | shared memory | int dot | matrix cores' (ggml-vulkan.cpp:7333 — emitted at GGML_LOG_DEBUG, mapped to level 0 by sk_common.cpp:96 and to logging.DEBUG by native.py:17-20, so the sink must not filter it; pin the format per ggml pin bump), or (b) time absolute throughput per type and stop pretending a ratio exists.

- **[high] ggml picks the Vulkan matmul path per (vendor, architecture, K, N, type) at runtime — a fixed-shape probe measures a path the real model may never take** — ggml_vk_should_use_mmvq (ggml-vulkan.cpp:9434-9470): Q6_K uses mmvq only on Intel; on NVIDIA n==1 with k<=4096 never uses mmvq; Q8_0/MXFP4 mmvq only on NVIDIA_PRE_TURING; n>1 always mmvq when integer_dot is present. The mmv path is taken only for ne11<=8 (mul_mat_vec_max_cols=8, lines 389/10062) and the coopmat mul_mm 'aligned' path needs ne10==kpad && ne01>8 && ne11>8 (9246). So the probe's M=1/M=256 at some fixed K (K=4096 sits exactly on the NVIDIA threshold) can report 'integer_dot fast' for Q8_0 on an RTX 4070 while llama's decode of that same Q8_0 model goes through dequant mmv because ggml decided so. Conversely a catalog author cannot statically write 'this rung benefits from vulkan:integer_dot' because whether it does is a runtime function of the GPU vendor/arch and the model's hidden/FFN dims (Qwen3.5-4B, EuroLLM, the transcribe.cpp encoders and audio.cpp LLM heads all differ). llama.cpp's own n_batch=512 (sk_translate.cpp:198) and TTS families' small batches (2-8 columns) hit yet other branches.
  *Suggestion:* Probe with the model's actual K/N pairs (read from GGUF metadata or stored per card) and at the M the stage actually runs (1 for LLM decode, n_batch for prefill, ~1500 for ASR encoders), reporting absolute µs per call. Drop the per-rung 'benefits from path X' field; the sidecar cannot know which path ggml will choose without running it.

- **[high] A relative fast/slow tri-state cannot decide the absolute goal (aggregate RTF < 1); the 'slow' threshold is unspecified** — The design skips a rung whose path is 'slow' relative to the generic path on the same device. The goal is absolute: seconds of compute per second of speech across ASR+MT+TTS. A Q8_0 rung that is 'slow' (generic path) on an RTX 4070 SUPER still runs 10x faster than real time; a Q4_K_M rung that is 'fast' on an Intel Xe iGPU (Vulkan device with uma=1, mem_total = system RAM, so the fit-walk in _llamacpp_variant_row happily recommends the largest quant) may still not keep up. Nothing in the design states the ratio at which 'slow' flips, nor how a ratio composes across three stages. The existing bench cache already holds absolute rtf/tps/tts numbers (accel.py:533-596) — the probe as specified produces a value in a different unit that the planner cannot combine with them.
  *Suggestion:* Make the probe emit absolute numbers per ggml_type: GB/s at M=1 (bytes of weights read per µs) and GFLOPS at the prefill M. Then estimate tokens/s per rung = bandwidth / bytes-per-token from the card's known size, and compare against the per-stage budget the same way resolve_translate's E6 tps comparison already does. Specify the threshold as an RTF margin, not a ratio.

- **[high] Metal vocabulary never discriminates on any Mac Sokuji ships to; the timing probe there costs a subprocess + metallib compile for zero decisions** — metal:simdgroup maps to has_simdgroup_reduction, which is the precondition for EVERY MUL_MAT/MUL_MAT_ID on Metal (`return has_simdgroup_reduction && op->src[0]->type != GGML_TYPE_NVFP4;` ggml-metal-device.m:1709-1711) and is true on Apple7+ = every Apple Silicon; metal:bf16 (has_bfloat, Apple6/Metal3) likewise. mac-x64 has no Metal lane at all (ggml_options.cmake:23 — CPU only), mac-arm64 is Apple Silicon only. The only Metal device that differs is the paravirtual CI VM, already excluded by _paravirtual_metal_only (planner.py:106-118). What actually broke Metal in practice was op coverage — DIAG_MASK_INF and leading-edge PAD needed patches (ggml_options.cmake:69-89), ggml_sub needing src1 cont (audiocpp_compat.h) — none of which a MUL_MAT micro-benchmark can observe. Meanwhile GGML_METAL_EMBED_LIBRARY=ON (ggml_options.cmake:121) means each probe subprocess recompiles the embedded Metal source at init ('compiled in %.3f sec', ggml-metal-device.m:584).
  *Suggestion:* Skip the timing probe on Metal entirely. If Metal risk must be gated, gate on op coverage: build the family's real graph (or a per-family op list) and walk ggml_backend_dev_supports_op — that is the one check that would have caught the DIAG_MASK_INF/PAD aborts before R36-style rulings.

- **[high] MUL_MAT is not the op mix for TTS or ASR, and the TTS ladder is q8_0/bf16/f16 — not the Q4_K→f16 ladder the design describes** — Every TTS card carries only q8_0 and bf16 (or f16 alone for supertonic) — catalog.py:1042-1143 — so 'ladder Q4_K_M -> Q5 -> Q6 -> Q8 -> f16/bf16' has two rungs for TTS and the decision is exclusively 'is bf16 usable here'. On Vulkan bf16 IS the device-variable rung (device->bf16, coopmat_bf16_support/coopmat2_bf16_support, ggml-vulkan.cpp:3850-3853, 6253, 7148) — but the known bf16 defect on Vulkan is numerical (moss_tts_nano bf16 peak 1.228 clips, CLAUDE.md known gaps), not speed, and a timing probe hides it. TTS hot paths are conv1d/im2col (the compat shim exists precisely because im2col dtype differs), flash-attention (Vulkan FA has coopmat2/coopmat1/scalar variants chosen per device), get_rows and the codec decoder; ASR encoders run M≈1500 prefill matmuls plus convs. A single-backend MUL_MAT at two shapes says nothing about whether FA falls to the scalar path or conv lands on a slow kernel on a given GPU.
  *Suggestion:* Scope the probe honestly: it can only rank LLM-style decode/prefill matmul for translate. For ASR/TTS keep the existing measured-RTF path (measure_rtf / measure_rtf_tts) as the only source of truth, and gate the bf16 TTS rung on a numerical check (compare a short synth against the q8_0 rung) rather than a timing ratio.

- **[medium] Cache key (device description, native version) misses the driver/ICD, env overrides, and the ggml pin — the facts that actually flip Vulkan paths** — ggml_backend_vk_get_device_description returns VkPhysicalDeviceProperties.deviceName only (ggml-vulkan.cpp:17898-17901) — no driverVersion, no driverID. coopmat gating is driver-dependent: AMD proprietary/AMDVLK → RDNA3 only, RADV → all; Intel Xe1 iGPU → only on the Windows proprietary driver (18940-18950). Switching RADV↔AMDVLK, a driver update that adds KHR_shader_bfloat16, or installing MoltenVK/lavapipe (device dedup + driver_priorities at 7494-7549) all change the answer under the same key. GGML_VK_DISABLE_*/GGML_VK_VISIBLE_DEVICES/GGML_VK_FORCE_MMVQ (6185-6459, 7084-7087, 7444) alter behaviour and device ordering and are not keyed. 'native version' must be the full sk_engine_versions string (ggml/lane pins, sk_common.cpp:153-166), not sk_version alone — note Machine.fingerprint today contains neither (accel.py:150-156). On macOS the OS version drives Metal compiler output.
  *Suggestion:* Key the probe on: machine.fingerprint + sk_engine_versions() + a per-device driver identity (add driverID/driverVersion/deviceUUID to sk_device — needs a new native accessor since ggml's public API does not expose them; the init log line at 7333 is the only free source) + the GGML_VK_* environment slice. Store the key material alongside the value so a stale entry is explainable.

- **[medium] Multi-GPU / iGPU+dGPU: the probe, the budget, and the load can each target a different device** — native.device_for(kind) returns the FIRST device of that kind (native.py:39-45); _quant_budget_bytes uses the LARGEST mem_total across machine.gpus (planner.py:227); Plan.device is the bare string 'vulkan' with no index. On a laptop with an Intel/AMD iGPU (uma=1, mem_total = system RAM) plus an NVIDIA dGPU, ggml-vulkan's ordering after UUID dedup and driver_priorities (7444-7549) can put the iGPU first: budget comes from the dGPU, the probe keyed by description runs on whichever the sidecar picks, and the load lands on the iGPU. ggml_backend_vk_init(size_t dev_num) (17870) takes a Vulkan-relative index, not sk_device.index — the exact trap sk_tts.cpp already documents at backend_relative_index (sk_tts.cpp:157-161). sk_init also lists IGPU-type devices as placement targets (sk_common.cpp:207-209), so this is not hypothetical.
  *Suggestion:* Have sk_probe_accel take the flat sk_device.index and open the backend via ggml_backend_dev_init(devs[index], NULL); carry the device index on Plan and on the probe result; make _quant_budget_bytes and device_for agree on one primary device. Treat uma=1 devices as 'unified' for the fit-walk the way Apple Silicon already is.

- **[medium] Probe cost is a per-subprocess fixed cost multiplied by path ids, with lazy per-shape pipeline compiles and no ggml-side pipeline cache** — Each subprocess pays: Python start + sokuji_native import + sk_init → ggml_backend_load_all_from_path (dlopens every CPU variant, Vulkan instance init and device enumeration; Metal compiles the embedded library). Vulkan pipelines are then compiled lazily per requested (type, M-bucket, wg size) through CompileTask threads (ggml_vk_load_shaders(device, requested), ggml-vulkan.cpp:2071/4164, 6143); grep finds no vk::PipelineCache in the backend, so cold-start cost depends solely on the driver's disk cache (absent on a fresh Windows install, first run after a driver update). The signature sk_probe_accel(device, path_id) implies one call — and, if each is containment-isolated, one subprocess — per path id per device: 5-8 path ids × devices × (two shapes × N iterations + compile). Nothing states when this runs relative to the first session; if it runs at hardware_info time it lands on the user's first click, and if it runs while a stage is loaded the timed loop shares the GPU with the live model. GPU DVFS: a median taken right after a short warm-up on a laptop in a low clock state yields a 'slow' verdict cached forever.
  *Suggestion:* One subprocess per device that answers ALL path ids (and both baselines via env) in a single sk_init; run it at idle after first launch with a deadline, never while a stage is loaded; warm up until timings stabilise (coefficient of variation bound), not a fixed count; report elapsed wall time per device in the cached record.

- **[medium] Crash containment conflates 'unsupported' with transient failure and can take the live session down with it** — A non-zero exit from the probe subprocess is ambiguous: GGML_ABORT on an unsupported op, a vk::OutOfDeviceMemoryError escaping as std::terminate when the probe allocates while the sidecar's real models hold VRAM, a driver crash, or a Python import failure all look the same, and the design caches the result per (description, native version) with no retry/expiry — a one-off OOM becomes a permanent 'unsupported' that hides a rung until the next wheel bump. ggml-vulkan writes some diagnostics to std::cerr rather than the ggml log (7455), so the parent must capture the child's stderr, not only the log sink. On Windows a hung compute shader triggers a TDR that resets the adapter for every process — the parent's live Vulkan context receives VK_ERROR_DEVICE_LOST — so 'subprocess' contains the SIGABRT but not the GPU reset.
  *Suggestion:* Cache 'unsupported' only when the child's captured log contains the GGML abort text naming the op; treat other non-zero exits as 'unknown' with bounded retry and an expiry. Run the probe only when the VRAM ledger (_LEDGER) is empty and no session is active. Bound each graph_compute with a watchdog well under the OS TDR threshold (2 s on Windows) so a stuck shader is killed by the parent before the driver resets the adapter.

- **[low] The closed tri-state cannot express the outcome that actually happens: scheduler reroute to CPU** — When a (op, type) is unsupported on the GPU inside a real llama.cpp/audio.cpp graph, ggml_backend_sched silently reroutes that node to the CPU backend (report §4 pitfall c) — the model still 'runs on GPU' from the sidecar's point of view (Plan.device = vulkan, ReadyMsg.device = vulkan) but with a per-token host round trip. The design's single-backend probe reports 'unsupported' for that case while the runtime outcome is 'supported, slow, partially on CPU'; the vocabulary has no value for it, and the renderer reason 'no accelerated path on this GPU' would be shown for a rung that in fact loads and runs. The reverse also occurs: a rung the probe marks 'slow' at M=256 may still be the fastest available for decode (M=1), where the ladder direction (smallest-first, opposite to the existing largest-first fit-walk in _fit_walk/_llamacpp_variant_row) then discards the better rung.
  *Suggestion:* Report per-rung an estimated tokens/s (or RTF) and let the planner threshold it; expose to the renderer a reason code plus the measured number ('~4 tok/s on this GPU') instead of a categorical path verdict.


### Lens: planner-integration (12)

- **[high] Filter placed before the downloaded-rung intersection silently switches to an undownloaded file** — Both fit-walk callers apply the `downloaded` restriction as an intersection over the candidate dict and fall back to the FULL dict when the overlap is empty: `_llamacpp_variant_row` (planner.py:518-527, `cached = {q: sz for q, sz in quants.items() if q in downloaded}; if cached: quants = cached`) and `_tc_pick_quant` (planner.py:264-269, same shape over `sizes_all`). If the new 'unsupported|slow' filter narrows `quants`/`sizes_all` first and the user's already-downloaded rung is the one probed slow, `cached` is empty, the code keeps the filtered set, and `_fit_walk` returns a rung that is NOT on disk. That is exactly the rule `_quant_budget_bytes`'s docstring forbids ('we always run exactly the file the user downloaded ... never a silent switch to a different model file') and it flips `test_resolve_tts_downloaded_restricts_the_fit_walk`, `test_resolve_asr_prefers_downloaded_quant_over_fresh_recommendation`, `test_resolve_translate_prefers_downloaded_quant_over_fresh_recommendation`, and the `downloaded_listed_only_quant_wins` / `downloaded_restricts_to_cached_quant` rows of TC_PICK_QUANT_DIRECT_MATRIX. `_tc_pick_quant` already has the right precedent: the curated filter shapes only `sizes` (fresh recommendations) while `sizes_all` feeds pin and downloaded.
  *Suggestion:* Specify that the accel filter is a FRESH-RECOMMENDATION filter only: in `_tc_pick_quant` apply it to `sizes` (never `sizes_all`); in `_llamacpp_variant_row` apply it only when the downloaded intersection is empty (or intersect first, filter second, and never let the filter empty a non-empty `cached`). Add a planner test: downloaded={slow rung} on a GPU machine must still return that rung.

- **[high] 'Unsupported' is skipped in the walk but still lands on the GPU tier through pin, downloaded, and override='gpu'** — Three paths bypass the recommendation walk and choose a (quant, tier) directly: `_tc_pick_quant` returns `pin` before any gating (planner.py:262 `if pin in sizes_all: return pin`); `_llamacpp_variant_row` returns `_row(pin)` which picks the best `_tier_available` tier (planner.py:497); `resolve_deployments`'s `_pinned` for override 'gpu' pins ANY accelerator row (planner.py:166-172) after `_llamacpp_quant` narrowed to the rank-default quant with no fit logic. The design only says the walk 'skips' an unsupported rung, so all three still place it on gpu-vulkan/gpu-metal. The consequence differs per stage and the design does not say which: sk_translate.cpp loads with `n_gpu_layers = -1` under llama.cpp's scheduler, so an op the GPU backend rejects silently runs on CPU (slow, not fatal); sk_tts.cpp has no scheduler and an unsupported op is a GGML_ABORT/SIGABRT (R36 evidence, planner.py:95-103). So 'unsupported' for TTS is a crash that pin/override can still reach.
  *Suggestion:* Define 'unsupported' as a per-(compute_type, tier) availability fact enforced where tiers are gated (a sibling of `_tier_available` that takes the Deployment, used by `resolve_deployments`'s `usable` filter, `_row()` in `_llamacpp_variant_row`, `select_variant.candidate`, and both `gpu_possible` checks), so pin/downloaded/override resolve to that rung's cpu row instead of aborting. Keep 'slow' as recommendation-only.

- **[high] Recommendation and runtime pick are the same functions called with different arguments from three sites, plus an override path with no walk at all** — `_h_models_catalog` computes `recommended` via `_llamacpp_variant_row(mdl, m, None, 0, budget)` / `_tc_pick_quant(mdl, m, None, budget)` (accel.py:806-810) with no `downloaded` and no reserve; `_h_list_variants` (legacy, still used by NativeModelClient.ts/nativeModelStore.ts) calls `select_variant(model, m, reserve, pin, budget_bytes=...)` with no `downloaded`; `resolve`/`resolve_translate`/`resolve_tts` wrappers (accel.py:230-262) pass `_downloaded_quants`. The explicit-override branch of `resolve_translate`/`resolve_tts` uses `_llamacpp_quant` (rank-default, planner.py:449-463) and then `resolve_deployments` — neither touches `_fit_walk`. Because planner.py is pure and `Machine` is frozen, probe results must arrive as a parameter: either a new `Machine` field (touching every `Machine(...)` fixture in test_planner.py, test_accel.py, test_characterization.py, test_platform_filter.py and `probe()`'s assembly) or a new kwarg on `_tc_pick_quant`, `_llamacpp_variant_row`, `select_variant`, `resolve`, `resolve_translate`, `resolve_tts`, `resolve_deployments` and their accel.py wrappers. The design's step 3 names only 'the planner's recommendation walk'.
  *Suggestion:* Enumerate the four call sites explicitly in the design and pick one injection mechanism. Add a consistency test asserting `_h_models_catalog`'s `recommended` equals `resolve_*`'s first plan compute_type when nothing is downloaded, on a fixture with a synthetic probe result.

- **[high] 'Runtime device placement continues via measured RTF' does not hold: TTS auto ignores the cache, and the CPU comparand is never measured in auto mode** — `planner.resolve_tts`'s auto branch never reads `cache` (planner.py:401-412) — the only bench use is `_apply_bench`, which runs inside `resolve_deployments` (ASR always; translate/tts only on explicit override), and the E6 tps swap in `resolve_translate` (planner.py:346-353). Both require BOTH the GPU entry and the CPU-floor entry (`_apply_bench`: `if cpu_rtf is None: return plans`). But `measure_rtf`/`measure_tps`/`measure_rtf_tts` run only on the plan that actually loaded (asr_engine.py:71, translate_engine.py:82, tts_engine.py:146), so a CPU entry exists only after the user once forced override='cpu' or a GPU load failed. In auto mode the ratchet never has the number it needs and never demotes. The design leans on this mechanism for the 'keeps up' half of its goal.
  *Suggestion:* Either extend `resolve_tts` auto to apply `_apply_bench` and add a one-off CPU-floor measurement policy (e.g. measure the cpu plan once when a GPU plan's RTF is >= a threshold), or drop the claim and make the accel probe the only speed signal. State which.

- **[high] The MUL_MAT probe cannot see the failure R36 encodes, and 'generic reference path on the same device' is not selectable through ggml's public API** — The paravirtual-Metal abort is on GGML_OP_NORM/RMS_NORM/ARGMAX (missing has_simdgroup_reduction; planner.py:95-103), not on MUL_MAT — a MUL_MAT-only `sk_probe_accel` reports 'fast' there, so `_paravirtual_metal_only` must stay and the probe cannot supersede it (contrary to the tests map's suggestion). For Vulkan, `ggml_backend_vk_device_supports_op` accepts Q4_K/Q8_0/BF16 MUL_MAT on every device (ggml-vulkan.cpp ~18140-18170), the mmv q4_k/q5_k/q6_k shaders are compiled into every device, and `.get_proc_address = NULL` (ggml-vulkan.cpp:18851) — there is no feature query and no knob to force the non-mmv/non-coopmat pipeline, so 'ratio vs the generic reference path' is only measurable across TYPES (bf16 vs q8_0 vs f16), which measures bytes moved, not whether an acceleration path exists. Metal DOES export `ggml_backend_get_features` via get_proc_address (ggml-metal.cpp:901-903), so Metal needs no timing at all — the design has it backwards for that backend.
  *Suggestion:* Split the probe: Metal and CPU answer from `ggml_backend_get_features` (include simdgroup_reduction/bfloat so R36 gets a structured signal alongside the string match); Vulkan answers from `VK_KHR_shader_integer_dot_product` / coopmat bits read via a small sk_ call into the device props instead of a timing race. If timing stays, define the comparand as another catalogued rung of the same model (q8_0 vs bf16), and probe at least one normalisation op so a paravirtual-class device can fail it.

- **[high] One ladder does not fit three stages, and it walks onto rungs the catalog forbids recommending** — The ladder Q4_K_M→Q5→Q6→Q8→f16/bf16 exists only for ASR (`_tc_row`, catalog.py:66-83), where q5_k_m and f16 are rank 0.5 listed-only and `_tc_pick_quant` excludes them from fresh recommendations (`_TC_CURATED_MIN_RANK`; TC_PICK_QUANT_DIRECT_MATRIX row `fresh_recommendation_never_listed_only`). Translate cards have exactly {q4_k_m, q8_0} (`_llm_translate_row`); TTS cards have {q8_0, bf16|f16} with supertonic (f16 only) and voxcpm1 (q8_0 only) single-rung (`_tts_gguf_row`). For TTS the whole decision is bf16 vs q8_0, and the path vocabulary answers 'fast' almost everywhere: Metal `has_bfloat` is true on every real Apple GPU (Apple6+/Metal3, ggml-metal-device.m:1050-1053; only the paravirtual shim clears it), Vulkan creates the BF16 dmmv pipeline unconditionally (ggml-vulkan.cpp:5243). Meanwhile `_fit_walk` is largest-first, so every GPU fixture in TTS_MATRIX resolves bf16 — a rung that moves ~1.7-2x q8_0's bytes at M=1 and is strictly slower on any bandwidth-bound device. The design's own assumption ('published ⇒ quality is close enough, speed decides') argues for smallest-that-keeps-up, which contradicts both 'preferring quality among rungs that keep up' and the text's 'smallest first' vs `_fit_walk`'s largest-first. A binary fast/slow/unsupported cannot encode 'both fast, q8_0 faster'.
  *Suggestion:* Decide per stage: keep ASR's curated set and largest-fit (K-quant paths matter there); for TTS/MT make the rule 'smallest rung whose path is fast' or drop the accel axis and use measured per-model RTF. Say explicitly whether the ladder respects `_TC_CURATED_MIN_RANK`.

- **[medium] No 'unknown probe result' semantics — the frozen characterisation suite and every synthetic Machine depend on it** — CPU_ONLY/CUDA_12GB/CUDA_24GB/APPLE_SILICON in test_characterization.py (and every `_nv_machine`/`Machine(...)` fixture elsewhere) carry no probe data. If 'no result' is treated as anything other than pass-through, every GPU row in TTS_MATRIX (all bf16), ASR_MATRIX and TRANSLATE_MATRIX flips, which the file's docstring forbids without justification. Separately, the suite calls the `accel.resolve*` wrappers with an autouse pin only on `_downloaded_quants`; if the wrapper reads accel-bench.json for cached probe results, the frozen suite becomes dependent on this box's ~/.cache — the exact host-dependence the docstring's determinism note guards against.
  *Suggestion:* Specify: absent/unknown probe result == 'generic' (no filtering). Add an autouse fixture in test_characterization.py pinning the probe cache to empty, mirroring the `_downloaded_quants` pin.

- **[medium] Probe cache key and trigger point are underspecified: fingerprint lacks native version and driver version, and a lazy probe stalls the first models_catalog RPC** — `Machine.fingerprint` (accel.py:152-156) hashes os/arch/apple/installed/tc_kinds/(kind:desc:mem_total) — no `sk_version()`, so a native bump does not invalidate bench entries; the design's (description, native version) key fixes that for probe rows but the Vulkan device description carries no driver version, and coopmat/integer-dot availability on NVIDIA/AMD changes with the driver. `bench_load`/`bench_save` are whole-file last-write-wins with no locking, and a subprocess writer racing `_measure` during a load loses updates. The design does not say WHEN the probe runs: `_h_models_catalog` is called on every Settings open; if it lazily runs N subprocesses each paying the first-time Vulkan pipeline compile (2-14s, W-1) the RPC blocks and the renderer shows an empty library.
  *Suggestion:* Key probe rows on (fingerprint, native version, driver/API version string from the device props) and write them from ONE place (sidecar startup or a dedicated RPC), never from `_h_models_catalog`; have the handler read only. Give the probe file its own path or an atomic rename.

- **[medium] Renderer has only two per-rung states; 'not recommended here' cannot ride `supported=false` without making the rung unpickable** — `VariantDropdown` renders `disabled={!v.supported}` and only calls `onPinVariant` when `v.supported` (NativeModelManagementSection.tsx:112-131); `deriveVariantRepos` (nativeModelStore.ts:216-228) drops a persisted pin whose variant is `supported === false`. `_h_models_catalog` sets `supported: True` unconditionally for GGUF cards (accel.py:817) and `variants[]` has no reason field; `variantData` (lines 523-550) fabricates a memory reason for every unsupported rung. So if 'no accelerated path on this GPU' is carried as supported=false the rung becomes unpickable and a user's pin is silently dropped — contradicting the planner's 'pin wins' — and `test_catalog_variants_translate_kind_included` (all supported True) flips.
  *Suggestion:* Add an optional `reason?: string` (or `reasonKey`) to `NativeModelInfo.variants` and a distinct 'notRecommended' flag; keep `supported` for won't-load only. Have `variantData` read the wire reason before falling back to its memory string, and render it on enabled options too.

- **[medium] No card-level state for 'nothing keeps up on this machine'** — catalog.py:970-984 records voxcpm2/index_tts2 at M4 Metal RTF 1.42/1.77 with CPU 3.27/4.94 — no rung and no device meets RTF<1, yet `_TTS_TIER_OVERRIDES` lists Metal and the planner recommends bf16 on gpu-metal. The design's per-rung reason ('no accelerated path on this GPU') is not the reason here; the card simply cannot keep up. Likewise the aggregate RTF<1 across ASR+MT+TTS has no computation site: `measure_rtf` (3s sine), `measure_tps`, `measure_rtf_tts` each run alone on an idle device, sessions run all three concurrently, and `_LEDGER` tracks bytes only.
  *Suggestion:* Add a model-level 'will not keep up' state derived from measured RTF (or a catalogued per-device RTF table like the one already in the comment) and surface it on the card, separate from the per-rung accel reason. Defer the aggregate-RTF goal or define how three isolated numbers combine.

- **[low] The catalogued per-rung path field cannot vary by tier inside the existing row builders** — `_tc_row`, `_llm_translate_row`, and `_tts_gguf_row` each emit `Deployment(..., tier, quant, ...)` in a `for tier in tiers` loop with identical fields per tier. A q4_k_m row needs `vulkan:kquant_mmv` on gpu-vulkan, a Metal id on gpu-metal, and `cpu:dotprod`/`cpu:i8mm` on cpu — different path ids for the same quant. The 'small field on Deployment' therefore has to be a per-backend map (the design's 'per backend' wording) or the builders must be rewritten; `_tier_available(tier, machine, backend)` already accepts `backend` and ignores it (planner.py:121), so a sibling taking the Deployment is the natural seam. Tests that pin row shape: `test_omnivoice_card_shape`, `test_tts_tier_overrides_default_is_cpu_only_for_unknown_family`, and the rank-convention tests in test_catalog.py.
  *Suggestion:* Make the field `accel_paths: Mapping[tier, tuple[path_id, ...]]` with default empty, defaulted in `Deployment` so every existing constructor call and test fixture stays valid.

- **[low] Tests that would flip or need new cases** — Must NOT flip: `test_tier_available_gpu_metal_excluded_on_a_paravirtual_device` and `test_paravirtual_exclusion_removes_gpu_metal_plans_end_to_end` (R36 stays); every row of TTS_MATRIX/ASR_MATRIX/TRANSLATE_MATRIX and TC_PICK_QUANT_MATRIX/LLAMACPP_VARIANT_ROW_MATRIX given unknown-probe pass-through; `test_catalog_variants_cpu_only_recommends_smallest` and `cpu_only_smallest_wins_ignores_budget` (the no-GPU→smallest rule is orthogonal since CPU `vec_dot` is non-NULL for every catalogued type — ggml-cpu.c:310-316 — so CPU can never be 'unsupported'). Will flip if semantics change: `test_list_variants_marks_supported_and_recommended`/`test_list_variants_dedupes_llamacpp` (`reason: "ok"`), `test_catalog_variants_translate_kind_included`/`test_catalog_variants_full_ladder_sorted_quality_desc` (all supported True), and `_FakeDev`/`_fake_native_module` positional constructors in test_accel.py:917-940 if `Device`/`Machine` grows a field. TS suites (nativeCatalog.test.ts, nativeModelStore.test.ts) are unaffected while new wire fields stay optional.
  *Suggestion:* List these in the design's test plan and re-record any characterisation row by running the code, per that file's docstring.


### Lens: product-and-ops (13)

- **[high] Smallest-first ladder flips every existing recommendation and makes already-downloaded models read as 'not downloaded'** — Today `_llamacpp_variant_row`/`_tc_pick_quant` (sidecar/sokuji_sidecar/planner.py) recommend the LARGEST rung that fits, and `_h_models_catalog` (accel.py:800-835) documents `recommended` as 'the stable default-download pick'. The design inverts this to Q4_K_M-first. On the renderer, `deriveVariantRepos` (src/stores/nativeModelStore.ts:216-223) computes each card's status repo as `pinned ?? recommended`; a user who downloaded the recommended rung has NO pin recorded. After the update the recommendation moves to q4_k_m, `model_status` is queried against the q4_k_m repo, the card flips to 'absent', the Download button reappears, `ensureSelectionReady` treats the stage as not ready, and the provider chip shows 'None' — the exact Fun-ASR regression the docstring at nativeModelStore.ts:195-201 was written to prevent. Meanwhile the sidecar's load path (`_downloaded_quants` restrict-if-overlap) would happily keep loading the q8_0 on disk. It also re-records every tuple in sidecar/tests/test_characterization.py (frozen by its own docstring) and contradicts `_h_models_catalog`'s 'must never flap → re-downloads' contract.
  *Suggestion:* Treat a rung already in the HF cache as the recommendation for that card (downloaded-wins, mirroring `_downloaded_quants` at load) so status never flips underneath a working install; only fresh cards get the new ladder. Ship an explicit migration note in the characterization re-record. Consider auto-writing a pin when the user downloads a rung so later recommendation moves are inert for them.

- **[high] Probe result cannot predict whether a model keeps up; the shipped catalog already has models that cannot keep up at ANY rung on any device** — sk_probe_accel returns a kernel-level ratio (fast/slow vs a generic path), not absolute throughput. The M4 numbers (voxcpm2 RTF 1.42, index_tts2 1.77 on Metal) are not accel-path failures — Metal simdgroup would probe 'fast' — they are model-compute failures, and the ladder would still recommend a rung. Worse, catalog.py:746-754 says voxcpm1/voxcpm2/irodori_tts/index_tts2 are absent from `_TTS_TIER_OVERRIDES` and resolve cpu-only today, where they are slower still. So four shipped cards accumulate lag on every machine, and nothing in the design (or the current UI — `formatRtf` in nativeCatalog.ts:307 renders rtf 1.42 as a neutral '0.7× realtime' with no warning class) tells the user before or after download. The ladder 'then existing fit-with-headroom rules' has no outcome for 'no rung keeps up here'.
  *Suggestion:* Add a per-(family, quant, device-class) published RTF table to the catalog (from the fleet runs already recorded in catalog.py comments) so `recommended` can become 'none — too slow for live speech on this machine' pre-download, and add a post-measure surface: when a stage's ready rtf ≥ ~0.8 (or aggregate ≥ 1) raise a warning state on the owning store rendered on the card/badge, not just a log line.

- **[high] Aggregate RTF (ASR+MT+TTS < 1) is not computable from what ready payloads carry** — ReadyMsg (nativeProtocol.ts:2-6) carries `rtf` for ASR/TTS and `tokensPerSec` for translation. (1) MT has no RTF: converting tps needs an expected tokens-per-second-of-speech (language-dependent — ja/zh targets tokenize 2-3x denser than the en→fr benchmark sentence in `measure_tps`) plus prefill cost, which for short utterances dominates and is not in tps at all. (2) ASR rtf is measured on a 3 s sine tone (`measure_rtf`, accel.py:533-546); the native roster includes autoregressive audio-LLM decoders (catalog.py:292/308/328) whose cost scales with emitted tokens, so a near-silent clip understates real-speech RTF. (3) TTS rtf is gen_time / OUTPUT audio seconds; the budget needs it scaled by translated/source duration ratio. (4) All three are measured in isolation with the GPU to themselves; in a session they contend on one device. The sum is therefore neither computable nor a safe bound.
  *Suggestion:* Define the budget explicitly: measure ASR on a bundled short speech clip, benchmark MT as ms-per-source-second (fixed source utterance, target language of the session, including prefill), report TTS as gen_ms per SOURCE second using a fixed translation pair, and put all three on the wire as `rtf` with a `contended: false` flag. Until then, do not present an aggregate number in the UI.

- **[high] Cached probe and bench entries do not invalidate on a native version bump; device description alone is the wrong key** — Machine.fingerprint (accel.py:152-157) hashes OS/arch/installed/tc_kinds/(kind, description, mem_total) — not `sk_version()` or engine pins. The design keys the new probe by '(device description, native version)' but says nothing about the EXISTING rtf/tps/tts entries that the 'measure-then-adapt' half depends on; after native 1.0.3 changes a kernel, the placement decision still reads 1.0.2 numbers forever. Description is also insufficient on its own: the same GPU under RADV vs AMDVLK vs proprietary NVIDIA, or a Mesa update, gains/loses coopmat/integer_dot support with an identical description string. The cache file lives in `~/.cache/sokuji-sidecar/accel-bench.json` (accel.py:486), outside userData, so it survives uninstall/reinstall and is shared between a dev checkout and the packaged app.
  *Suggestion:* Fold `native.module().version()` + engine_versions + the backend's driver/API version (ggml_backend_dev_props / Vulkan driverVersion+driverName, Metal OS build) into a single cache-generation prefix applied to every namespace ('', 'tps:', 'tts:', and the new probe ns), and move the file under the sidecar bundle's userData dir so a bundle upgrade or uninstall clears it.

- **[high] First-run probe blocks the Settings model library and Start button with no progress UI** — The design runs probes 'for every path id referenced by any catalogued rung' at catalog time. `_h_models_catalog` is on the sidecar-ready critical path: nativeModelStore.ts:440-470 awaits three models_catalog calls before setting `sidecarStatus: 'ready'`. Each Vulkan/Metal probe is a subprocess that must dlopen the wheel, `sk_init` (loads all backend modules), and compile a MUL_MAT shader per ggml type — on NVIDIA the cold pipeline-cache compile is 2-14 s per kernel (catalog.py:930-932, W-1); with ~5 Vulkan paths × 2 shapes × N repeats, first launch after install AND after every sidecar bundle update could sit for 30-60 s with the library empty and the user staring at a spinner (or worse, at 'unavailable' if a WS timeout fires). There is no spec for a timeout, a progress message, or what the UI shows while results are pending.
  *Suggestion:* Run probes lazily off the critical path: emit the catalog immediately with `accel: 'pending'` per rung, run probes in a background task, push a `models_catalog_result` refresh when done, and gate only the 'Recommended' star on completion. Cap each subprocess with a hard timeout and cache a timeout as 'unknown' (not 'unsupported').

- **[medium] An aborting or hanging probe subprocess is not cached, so it re-runs every catalog fetch; probes must honour the paravirtual exclusion** — A GGML_ABORT in the probe child is a SIGABRT; the design states the subprocess isolation but not the result mapping. If an abort maps to 'unsupported' but is not persisted (e.g. because the parent only writes successful results), every `models_catalog` call re-spawns a crashing child. A hung driver (Intel iGPU Vulkan is a known offender) blocks the executor with no timeout. Also, `_tier_available` excludes /paravirtual/i Metal devices (planner.py:106-142) precisely because a plan there hard-aborts — the probe must consult the same gate or CI/VM users get an aborting subprocess per path on every launch.
  *Suggestion:* Persist abort/timeout outcomes as first-class statuses ('unsupported' for SIGABRT, 'unknown' for timeout) under the same cache key; skip devices `_tier_available` rejects; capture the child's stderr (which carries the aborting op name via `log_line`) into the cached record for bug reports.

- **[medium] 'Not recommended here' needs a third variant state and a reason CODE on the wire, not free text** — VariantDropdown (NativeModelManagementSection.tsx:135-140) renders a reason ONLY for `!v.supported` rungs, which are also disabled — there is no 'selectable but not recommended' rendering. If the new rung state is expressed as `supported: false`, the user cannot pin a rung that would run (just slower), and the `!gpuFits` note 'No GPU variant fits — runs on CPU' (line 148) becomes a lie. `NativeModelInfo.variants` (nativeProtocol.ts:41) carries no reason field, and the legacy `list_variants_result` path sends English free text ('no usable GPU', accel.py:659-663). All five existing models.* keys are present in 30 locale files; a sidecar-authored string would be the first un-localised user-facing text on the card, and the card already has one hardcoded 'Requires GPU' span (line 366) as a precedent not to repeat.
  *Suggestion:* Add `reason?: 'no_accel_path' | 'accel_slow' | 'wont_fit' | ...` (a closed enum) plus `accelStatus` to the variants wire shape; keep `supported` = 'can load'; render a non-disabled option with a muted reason line and keep the pin allowed. Add `models.variantNoAccelPath` / `models.variantAccelSlow` to all 30 locales in the same PR.

- **[medium] When every GPU rung is skipped, the renderer silently crowns the largest download as 'Recommended'** — `_h_models_catalog` marks `recommended: ct == rec`; if the ladder skips every rung on the target device and the sidecar emits no recommended entry, both `variantData` (NativeModelManagementSection.tsx:546) and `deriveVariantRepos` (nativeModelStore.ts:223) fall back to `vs[0].id` — and `vs` is sorted size-DESCENDING, so the biggest file (bf16 / f16) becomes the default download and the status repo. Whole-card gating (`hardwareGated`, nativeCatalog.ts:221) is tier-level and unchanged by the design, so the card also looks fully available.
  *Suggestion:* Make the sidecar always emit exactly one `recommended` (falling back to the CPU-tier pick, smallest rung, when no GPU rung qualifies) and change both renderer fallbacks from `vs[0]` to the smallest rung; add a `recommendedTier` so the card can show 'runs on CPU here'.

- **[medium] 'Measure-then-adapt' never fires: the CPU floor is never benchmarked unless the user manually runs on CPU** — `_apply_bench` (planner.py:598-611) and the tps swap in `resolve_translate` (planner.py:344-352) only demote a GPU plan when BOTH the GPU and the CPU entries exist in the cache. `measure_rtf`/`measure_tps`/`measure_rtf_tts` run only on the plan that actually loaded (asr_engine.py:66, translate_engine.py:83, tts_engine.py:145). On a fresh machine the CPU floor is never measured, so a slow GPU rung is never moved — the design's claim that 'device/tier placement adapts freely from measured RTF' is not true of the code it says it relies on. And on the M4 case, CPU would be slower anyway, so 'adapt' has no target.
  *Suggestion:* Either drop the claim from the design, or add an explicit one-time CPU-floor measurement (opt-in, background, after the first session) so `_apply_bench` has something to compare; and define what happens when both tiers are ≥ 1 (see the 'cannot keep up' finding).

- **[medium] Re-download suggestion has no phrasing, no gate, and orphans the old rung on disk** — The design says quant is a download-time recommendation but never specifies the UX when the recommendation changes for a model the user already has: who prompts, with what copy, whether it counts against a metered connection, and what happens to the previous file. `deleteModel(spec.downloadId, chosenVariant?.repo)` (NativeModelManagementSection.tsx:~400) targets the CHOSEN rung only, so after switching to q4_k_m the q8_0 GGUF (up to 8 GB for hy-mt2-7b) stays in the HF cache with no UI to remove it. The consent gate is fine (`hasAcceptedLicense` is keyed by downloadId, line 244, so no re-prompt), but the cross-rung disk story is missing.
  *Suggestion:* Specify: never auto-download; show a passive 'A smaller rung is now recommended for this GPU (saves X GB, ~Y% faster)' line on the card with a single 'Switch' action that downloads the new rung, then offers to delete the old one; list cached-but-unchosen rungs in the picker with a size and a delete affordance.

- **[medium] Probe outcome and subprocess output never reach the Logs panel a bug report is pasted from** — Diagnostics policy: renderer-side failures go through reportError/reportWarning; sidecar contexts keep their channel and the renderer-side caller reports. Today the sidecar's stderr (including any GGML abort text) goes to Electron main's console (electron/native-host-manager.js:130) and never to LogsPanel; `hardware_info_result` carries nativeVersion/lane/preferredDevice (nativeProtocol.ts:53-60) but the connect-time `local.native.hardware` event (LocalNativeClient.ts:89-96) forwards only os/arch/gpus/backends. Nothing in the design puts per-path fast/slow/unsupported + ratio + child stderr on any wire, so 'why is q4_k_m not recommended on my box' cannot be answered from a pasted log, and a re-probe cannot be requested.
  *Suggestion:* Add `accelProbe: {deviceKey, nativeVersion, driver, results: {pathId: {status, ratio, ms, stderrTail}}}` to `hardware_info_result`; include it in the `local.engine.ready` realtime event nativeModelStore already emits; surface a probe that ended in 'unknown' (timeout/crash) via `reportWarning('NativeModelStore', …, {dedupeKey:'accel.probe'})`; add a 'Re-run hardware probe' action that calls probe(force=True) + the new probe with force.

- **[low] CPU probe as specified answers 'fast' for every type, so it can never skip a rung** — ggml-cpu registers a `vec_dot` for every quantised type in `type_traits_cpu` (generic C with SIMD `#ifdef`s inside), so `ggml_get_type_traits_cpu(type)->vec_dot != NULL` is always true; the discriminating information is only the CPU-variant feature bits, and the mapping from feature bits to 'this type is fast' (dotprod → Q4_K/Q8_0 ARM fast paths, i8mm → Q4_0 gemm, AVX-VNNI → Q8) is a table someone must hand-maintain against each ggml pin — exactly the kind of drift the exact-text patch specs exist to catch. Meanwhile CPU is bandwidth-bound and `_tc_pick_quant` already picks the smallest rung on CPU, so the probe's CPU answer changes nothing.
  *Suggestion:* Drop the CPU half of `sk_probe_accel` for the first cut (CPU = smallest rung, as today) or time it like the GPU paths; if the feature-bit table stays, pin it with a test that fails when the ggml pin bumps.

- **[low] 'Slow' threshold and reference path are unspecified but drive a user-facing re-download** — The design says the timed probe is 'compared against the generic reference path on the same device' and yields fast|slow|unsupported, but does not say what the reference is for each path (for Vulkan Q4_K the fallback is dequant + f16 matmul; for Metal bf16 it is f16), what ratio boundary separates fast from slow, or how run-to-run noise (1.2-4.3x spread measured on GB10 when oversubscribed) is handled. A rung flipping between fast and slow across reboots would flip the recommendation and therefore the card's status repo (see the first finding) — precisely the flapping `_quant_budget_bytes` was designed to avoid.
  *Suggestion:* Pin the reference and threshold per path id in the closed vocabulary (e.g. ratio ≥ 1.5 = fast, ≤ 0.9 = slow, else 'neutral' which does not skip), require the probe to run at the 12-thread knee with the GPU otherwise idle, and treat a neutral/unknown result as 'do not skip'.

### Lens: quality (19)

- **[high] Linking `Vulkan::Vulkan` into `libsokuji_native` contradicts §6 "loader absent → known = 0" and the wheel's dependency policy** (`§3.1 Vulkan source — "`sokuji_native` links `Vulkan::Vulkan` when `SOKUJI_GPU_RESOLVED` is `vulkan`" vs §6 "Vulkan loader absent. `known = 0`"`) — A DT_NEEDED / import on `libvulkan.so.1` / `vulkan-1.dll` makes `import sokuji_native` fail outright on a box without the loader — native becomes absent, not `known = 0`, and premise 5 ("an absent profile changes nothing") is violated because the whole wheel is gone. Today the loader is a dependency of the dlopen'd `ggml-vulkan` module only: `native/ci/check_linux_deps.py:11-14` allows `libvulkan.so.1` precisely because "ggml skips a module it cannot dlopen". - **[high] The `bf16` feature gate refuses rungs ggml can execute and duplicates op coverage with a different answer** (`§3.3 `_deployment_available` — `if d.compute_type == "bf16" and "bf16" not in dev.features: return False`; §3.1 `SK_FEAT_BF16 /* Vulkan: VK_KHR_shader_bfloat16 */``) — On Vulkan, ggml's `supports_op` accepts `MUL_MAT` with a BF16 `src0` unconditionally (ggml-vulkan.cpp:15782 in the inspected tree); the scalar `matmul_bf16` pipeline is created in the no-coopmat branch (ggml-vulkan.cpp:4290) and `VK_KHR_shader_bfloat16` only gates the coopmat bf16 variants (`coopmat_bf16_support`).
