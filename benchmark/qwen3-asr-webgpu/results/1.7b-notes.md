# Qwen3-ASR-1.7B in layout v2 — export and 0.6B comparison

**Date**: 2026-09-03. Question asked: export the 1.7B the same way as the 0.6B (layout v2) and
measure speed and GPU memory relative to the 0.6B.

Working dir on the GB10: `/home/jiangzhuo/.claude/jobs/c6177dc7/tmp/qwen3-asr-onnx/output/v2-1.7b`
(v1 FP32 graphs in `output/qwen3-asr-1.7b`). Nothing uploaded to the Hub yet.

## Architecture (from the HF config)

| | 0.6B | 1.7B |
|---|---|---|
| AuT encoder | 18 layers, d 896, 14 heads, ffn 3584, out 1024 | 24 layers, d 1024, 16 heads, ffn 4096, out 2048 |
| decoder | Qwen3-0.6B: 28 layers, hidden 1024, 16 q / 8 kv heads, head 128, ffn 3072 | Qwen3-1.7B: 28 layers, hidden 2048, 16 q / 8 kv heads, head 128, ffn 6144 |
| embedding | tied, 151936 × 1024 | tied, 151936 × 2048 |
| KV cache per token | 224 KB fp32 / 112 KB fp16 | **identical** (same layers, kv heads, head dim) |

So the extra memory of the 1.7B is all weights and activations; a 20 s utterance costs the
same ~64 MB of fp32 KV cache on both.

## Export — same pipeline, scripts made size-agnostic

Steps as in `v2-notes.md` for the 0.6B: `export.py` (v1 FP32) → native fp16 encoder →
`export_v2.py` (prefill on `input_embeds`) → `optimize_graphs.py` (RMSNorm / encoder fusion,
in place) → `embed_int8.py` → `quantize_v2.sh` (int4 RTN block 32, shared weights) →
`q4f16_v2.sh` → `make_prompt_config.py`. Wall time after the 4.7 GB download: ~9 min for v1,
~5 min for everything after (the 6.5 GB FP32 decoders quantize in under a minute).

Four scripts had the 0.6B hidden size (1024) hard-coded (`make_prompt_config.py`,
`embed_int8.py`, `check_tokens.py`, `decode_v2.py`); they now read `decoder.hidden_size` /
`vocab_size` / `num_layers` / kv dims from the pipeline's `config.json`, and the two `.sh`
steps take the model dir as an argument (`QWEN3_ASR_ONNX_DIR`, `PY` env). Regression: the
parameterised scripts regenerate the shipped 0.6B `prompt_config.json` identically and the
int8 embedding byte for byte.

Pipeline facts for the 1.7B: fusion removed 26.5 % of encoder nodes and 30–31 % of decoder
nodes (same as 0.6B); int8 embedding max |w| 0.303, max dequant error 1.19e-3; `onnx.checker`
rejects the contrib SimplifiedLayerNormalization as before, ORT loads every session; the 16
language-prefix id triples are identical to the 0.6B's (same tokenizer).

### Token-exact checks (CPU, `check_tokens.py`, `results/1.7b-check-tokens.txt`)

- v2 FP32 vs v1 FP32: **identical** on jfk / ja-fleurs1828 / zh-fleurs1883 (30, 27, 34 tokens).
- int4 and q4f16: identical on en and zh; the Japanese clip differs at token 7
  (FP32 「適体適環境コース」 vs int4 「適体的環境構成」; reference 「敵対的環境コース」 —
  a hard phrase both get partly wrong). Same class of int4 wobble as the 0.6B's one
  punctuation token.
- Forced `zh` prefix runs the forced path on all three clips (the "DIFF at token 0" is the
  prefix itself being absent from the generated ids, by design).

## Browser benchmarks — speed

Spike page (`www/main.js`, layout v2), 13 clips (8 ja, 4 zh, 1 en), medians over the warm
clips, both models run back to back on the same box in the same session. GB10 = its own
NVIDIA GPU through `chromium_headless_shell` + Vulkan (no shader-f16, so q4 only); Mac and
Windows = Chrome 152, models served from the GB10 over the LAN (hence the load times).

| | GB10 q4 | RTX 4070 SUPER, Ubuntu, q4 | Mac mini M4 q4f16 | RTX 4070 SUPER, Windows, q4f16 |
|---|---|---|---|---|
| ms/token 0.6B → 1.7B | 19.9 → 22.4 (×1.13) | 17.2 → 19.6 (×1.17) | 16.2 → 23.4 (×1.43) | 17.2 → 24.4 (×1.34) |
| median RTF | 0.075 → 0.093 | 0.067 → 0.083 | 0.076 → 0.111 | 0.071 → 0.092 |
| median prefill (10–15 s clip) | 43 → 63 ms | 29 → 47 ms | 96 → 234 ms | 31 → 52 ms |
| median encoder | 32 → 42 ms | 20 → 32 ms | 79 → 112 ms | 21 → 31 ms |
| load (sessions + weights) | 3.5 → 5.3 s | 13.9 → 27.2 s (LAN fetch) | 8.7 → 18.4 s (files browser-cached; 14 → 33 s on first fetch over the LAN) | 9.5 → 20.0 s (browser-cached) |
| mean CER, all 13 | 0.126 → **0.075** | 0.133 → **0.082** | 0.127 → **0.080** | 0.123 → **0.079** |
| mean CER, ja only | 0.147 → **0.070** | 0.159 → **0.082** | 0.149 → **0.079** | 0.143 → **0.077** |

The Windows column took three attempts to get: 192.168.1.13 is one machine that dual-boots —
`jiang@` is Windows, `jiangzhuo@` is Ubuntu 22.04 — and it had been rebooted into Ubuntu
mid-session (the "host key changed" + "permission denied" pair is the tell-tale, not a broken
sshd). Back under Windows, Chrome 152 + NVIDIA 610.88 hand out the hardware adapter only on
about every other headless launch (`probe.html` alternates nvidia / null), which showed up as
"WebGPU adapter unavailable" and ORT's "Failed to get GPU adapter"; `fleet_run_win.sh` now
retries the run on that signature. An earlier, unpaired 7-clip 1.7B run had read 18.7 ms per
token; the full paired run above (24.4) supersedes it.

**Same 4070 under Ubuntu (Chrome 151, NVIDIA 580):** headless Chrome only ever gets a
SwiftShader adapter over SSH (every Vulkan/ANGLE/ozone flag combination tried), the Playwright
headless shells no adapter at all; a real Chrome window on the box's logged-in X session
(`ubuntu_run_page.sh`: `NO_HEADLESS=1 DISPLAY=:1 XAUTHORITY=/run/user/1000/gdm/Xauthority`)
gets the NVIDIA lovelace adapter — **without `shader-f16`**, exactly like the GB10's Vulkan
adapter. So on Linux the 4070 runs q4 only, and the fp16 variants of both models are a
Windows (D3D12) / macOS (Metal) affair on NVIDIA hardware. The Ubuntu q4 numbers are below the
memory table; GPU memory there comes from `nvidia-smi` (total used, discrete GPU, idle desktop
≈ 0.87 GB baseline), the cleanest accounting of the four boxes.

(GB10 numbers are the third, clean run — the first two had stale `headless_shell` processes
from earlier sessions alive on the box; they did not change speed: 19.5 / 20.8 / 19.9 ms per
token for the 0.6B across the three runs, 23.6 / 23.3 / 22.4 for the 1.7B.)

Reading: the step loop is dispatch-bound on every GPU, so a decoder with ~2.8× the weights
costs only 13–17 % more per token in q4 on the NVIDIA cards and 34–43 % in q4f16 (4070 under
Windows, M4); prefill and the encoder, which are
compute-bound, scale closer to the parameter ratio (1.6–2.4×). Quality is where the 1.7B pays
off — on the Japanese FLEURS clips it fixes exactly the proper-noun / kana slips the 0.6B
makes (カタルーニャ語, マリア像, 知性は…, 家計を…), halving the Japanese CER; en and zh were
already near-perfect on the 0.6B.

## Browser benchmarks — memory

WebGPU exposes no memory API, so every figure below is an OS-side measurement of the Chrome
that ran the page (samplers and raw series in `results/1.7b-memory/`). Three different
accountings, none directly comparable with the others:

| box | what is measured | 0.6B | 1.7B | Δ |
|---|---|---|---|---|
| RTX 4070 SUPER (12 GB), Ubuntu | `nvidia-smi` total GPU memory in use minus the idle-desktop baseline (0.9 GB), peak / steady during decode | +3.2 / +3.1 GB (q4) | +5.0 / +4.9 GB (q4) | **+1.8 GB** |
| RTX 4070 SUPER (12 GB), Windows | *dedicated* GPU memory of Chrome's GPU process, the Task-Manager counter (`GPU Process Memory\Dedicated Usage`); peak, and the range seen while the clips decode | 1.92 GB peak, 1.5–1.9 GB while decoding (q4f16) | 3.33 GB peak, 2.9–3.3 GB while decoding (q4f16) | **+1.4 GB** |
| Mac mini M4 (unified) | phys_footprint of the harness Chrome's GPU process (`footprint -p`, includes IOAccelerator/Metal), peak / steady state during decode | 2.25 / 2.22 GB (q4f16) | 3.91 / 3.86 GB (q4f16) | +1.65 GB |
| GB10 (unified, 121 GB) | system-wide MemAvailable drop while the page runs — the only number on this box that includes Vulkan allocations, but it also includes the page's own copies of the model bytes | 6.5 GB peak / 6.4 GB steady (q4) | 9.3 GB peak / 9.2 GB steady (q4) | +2.8 GB |
| GB10 | RSS of the harness GPU process (does not see device-local Vulkan memory) | 1.17 GB | 1.47 GB | +0.3 GB |
| files | encoder + decoder weights that end up in GPU buffers | 1.13 GB q4 / 0.72 GB q4f16 | 2.37 GB q4 / 1.63 GB q4f16 | +1.24 GB / +0.91 GB |

The Windows counter is sampled by `Get-Counter`, which costs ~1.6 s per sample, and a whole
13-clip run lasts only 25–32 s on this card, so the "while decoding" range rests on 5–8
samples; the peak is exact. The 0.6B Windows series was taken with a clean box (the
stale-Chrome contamination described below was on the Mac and the GB10).

What the numbers say: on a discrete card the 1.7B costs **+1.4 GB (q4f16, Windows: 1.9 →
3.3 GB)** to **+1.8 GB (q4, Linux: 3.1 → 4.9 GB)** of GPU memory over the 0.6B; the M4's
GPU-process footprint says the same in q4f16 (2.2 → 3.9 GB, +1.65 GB). Each delta is the
weight delta (+0.91 GB q4f16 / +1.24 GB q4) plus the larger activation and intermediate
buffers of a hidden-2048 decoder and a 24-layer encoder, and every model/variant sits at
~2.5–3× its raw weight bytes (ORT-web keeps staging copies, Dawn its pools). On the same 4070,
q4f16 needs about a third less than q4 for both models (smaller encoder, fp16 activations).
Practical budget: **~3.5 GB of VRAM for the 1.7B q4f16, ~2 GB for the 0.6B q4f16**; ~5 GB and
~3 GB in q4 (which is what Linux and the GB10 get, lacking shader-f16). The system-RAM cost on
unified-memory machines (GB10: 6.4 → 9.2 GB for this page, +2.8 GB) adds the page's own
copies of the fetched model bytes and the wasm heap, which the product worker shares in
shape, so a UMA laptop needs ~3 GB more free RAM for the 1.7B than for the 0.6B.

Measurement trap found on the way: an interrupted `run_page.py` / `run_page.mjs` (dropped
SSH, timeout kill) left its headless Chrome alive — two on the Mac for 16 hours, six
`headless_shell` on the GB10 — each holding a model in its GPU process, which silently
inflated and confused the first memory runs. `run_page.*` now kill Chrome from an
`atexit`/`exit` hook and on SIGHUP/SIGTERM, and the fleet scripts kill any leftover
`--remote-debugging-port` Chrome before a run (`kill_stale_chrome.ps1` on Windows).

## Bottom line

| | 0.6B | 1.7B |
|---|---|---|
| download (q4f16 / q4) | 0.89 / 1.30 GB | 1.96 / 2.70 GB |
| ms per generated token | 16–20 | 20–24 (+13–17 % NVIDIA q4, +34–43 % q4f16) |
| prefill for a 10–15 s utterance | 30–100 ms | 50–230 ms |
| RTF (warm, 13 clips) | 0.067–0.076 | 0.083–0.111 |
| GPU-resident weights (q4f16 / q4) | 0.72 / 1.13 GB | 1.63 / 2.37 GB |
| dedicated GPU memory, 4070 under Windows (q4f16) | 1.9 GB | 3.3 GB |
| GPU memory in use, 4070 under Linux, steady (q4) | 3.1 GB | 4.9 GB |
| Chrome GPU-process footprint on the M4, steady (q4f16) | 2.2 GB | 3.9 GB |
| Japanese CER (8 FLEURS/CV clips) | 0.147 | 0.070 |

The 1.7B is a quality tier, not a cost tier: half the Japanese errors for ~1.2–1.4× the
per-token time and ~2.2× the download and GPU footprint. Both variants of the 1.7B layout v2
are ready in the working dir; nothing is on the Hub yet.
